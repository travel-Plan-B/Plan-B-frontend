# Git 협업 운영 가이드

## 1. 목적과 결론

이 문서는 Next.js 프론트엔드 프로젝트를 FE 2명과 BE 1명이 빠르게 개발하면서도, 코드 리뷰와 포트폴리오에 활용할 협업 이력을 명확히 남기기 위한 최소 규칙이다.

**이 프로젝트는 `develop` 없이 `main + 작업 브랜치`를 사용하고, PR은 기본적으로 `Squash and merge`한다.** 모든 수정에 Issue를 강제하지 않되 기능, 버그, 구조 변경은 작업 브랜치와 PR로 검토한다.

### `develop` 사용 여부 비교

| 방식                           | 장점                                              | 단점                                               | 적합성                                    |
| ------------------------------ | ------------------------------------------------- | -------------------------------------------------- | ----------------------------------------- |
| `main + 작업 브랜치`           | 흐름이 짧고 배포 기준이 명확하며 관리 비용이 작다 | 미완성 변경이 합쳐지지 않도록 PR 리뷰가 필요하다   | **FE 2명 규모에 권장**                    |
| `main + develop + 작업 브랜치` | 배포 후보와 개발 통합본을 분리할 수 있다          | 동기화, 충돌 해결, 이중 PR 등 관리 비용이 늘어난다 | 정기 릴리스나 여러 개발 팀이 생길 때 검토 |

현재 규모에서는 `develop`이 제공하는 이점보다 관리 비용이 크다. `main`을 항상 실행 가능한 상태로 유지하고, 미완성 기능은 작업 브랜치에 두거나 필요한 경우 feature flag로 숨긴다.

## 2. 브랜치 전략

### `main`

- 리뷰와 검증을 마친 코드가 모이는 기준 브랜치다.
- 항상 빌드 및 실행 가능한 상태를 유지한다.
- 기능 개발, 버그 수정, 리팩터링, 설정 변경은 원칙적으로 직접 push하지 않는다.
- GitHub 설정이 가능하다면 PR과 최소 1명의 승인을 요구하는 branch protection을 권장한다. 이 문서는 저장소 설정 변경을 강제하지 않는다.

문서 오탈자, 주석 한 글자 수정처럼 **동작에 영향이 없고 리뷰 가치가 거의 없는 변경**은 팀에 알린 뒤 `main`에서 바로 처리할 수 있다. 다만 설정, 의존성, 공통 타입, UI, 애플리케이션 코드는 변경량이 작아도 작업 브랜치와 PR을 사용한다.

### 작업 브랜치 생성 시점

Issue 또는 독립적으로 설명할 수 있는 작업을 시작하기 직전에 최신 `main`에서 생성한다. 한 브랜치는 한 목적만 다루고, merge 후 삭제한다. 1~3일 이상 오래 열어 두기보다 리뷰 가능한 단위로 나눈다.

형식은 `<prefix>/<kebab-case-summary>`다. Issue 번호는 선택적으로 `<prefix>/<issue-number>-<summary>`처럼 붙일 수 있다.

| Prefix      | 용도                          | 예시                             |
| ----------- | ----------------------------- | -------------------------------- |
| `feat/`     | 사용자 기능 추가·변경         | `feat/recovery-form`             |
| `fix/`      | 버그 수정                     | `fix/recommendation-card-layout` |
| `refactor/` | 동작을 바꾸지 않는 구조 개선  | `refactor/recovery-state`        |
| `chore/`    | 도구, 설정, 의존성, 폴더 정비 | `chore/project-structure`        |
| `docs/`     | 문서만 변경                   | `docs/git-workflow`              |
| `test/`     | 테스트 추가·수정              | `test/recovery-form`             |

- 영문 소문자와 숫자, 하이픈만 사용한다.
- 이름만 보고 목적을 알 수 있게 하며 `feature/test`, `fix/bug`처럼 모호한 이름은 피한다.
- 여러 prefix에 해당하면 작업의 주목적을 기준으로 선택한다.

## 3. Issue 운영 기준

Issue는 작업의 배경, 범위, 완료 조건을 팀이 공유하거나 포트폴리오에 의사결정 이력을 남길 가치가 있을 때 만든다.

### Issue가 필요한 작업

- 새 화면, 사용자 기능, API 연동
- 재현과 확인이 필요한 버그
- 여러 파일이나 공통 구조에 영향을 주는 개선·리팩터링
- FE/BE 협의, 우선순위 또는 일정 추적이 필요한 작업
- 한 번에 끝나지 않거나 후속 작업이 예상되는 작업

오탈자, 단순 문구 교체, 명백한 한두 줄 수정처럼 논의와 추적 가치가 낮은 작업은 Issue 없이 작은 PR 또는 예외적인 직접 수정으로 처리할 수 있다. 작은 수정 여러 개를 Issue 수를 늘리기 위해 억지로 분리하지 않는다.

### 제목과 분류

형식은 `[Type] 무엇을 하는지`로 작성한다.

```text
[Feat] 상세 복구 일정 입력 구현
[Fix] 추천 카드 정렬 오류 수정
[Improve] 복구 폼 모바일 사용성 개선
[Refactor] 복구 상태 관리 구조 개선
[Docs] Git 협업 가이드 작성
```

Issue 본문에는 최소한 다음 내용을 적는다.

- 배경/문제: 왜 필요한가
- 작업 내용: 포함할 범위
- 완료 조건: 확인 가능한 체크리스트
- 참고: 디자인, API 명세, 관련 논의 링크(있는 경우)

운영 메타데이터는 필요한 만큼만 사용한다.

- **Assignee:** 실제 담당자 1명을 기본으로 지정하고 공동 작업이면 추가한다.
- **Label:** 종류(`feat`, `bug`, `refactor`, `docs` 등) 또는 영역(`frontend`, `backend`)을 검색할 필요가 있을 때 사용한다. 제목 Type과 중복되더라도 보드 필터에 유용할 때만 붙인다.
- **Milestone:** 스프린트, MVP, 시연일처럼 명확한 목표가 있을 때만 사용한다. 모든 Issue에 강제하지 않는다.

## 4. Commit convention

형식은 `<type>: <한국어 명령형 요약> (#이슈번호)`다. 모든 일반 작업 커밋은 연결된 GitHub Issue 번호를 메시지 마지막에 하나만 적는다. 제목은 무엇이 바뀌었는지 구체적으로 쓰고 마침표는 생략한다.

| Type       | 의미                               |
| ---------- | ---------------------------------- |
| `feat`     | 사용자 기능 추가·변경              |
| `fix`      | 오류 수정                          |
| `refactor` | 동작 변화 없는 코드 구조 개선      |
| `chore`    | 빌드, 설정, 의존성, 개발 환경 작업 |
| `docs`     | 문서만 변경                        |
| `style`    | 로직 변화 없는 서식·스타일 정리    |
| `test`     | 테스트 추가·수정                   |

- type은 위 목록의 소문자만 사용한다.
- type 뒤에는 콜론과 공백(`: `)을 쓴다.
- subject는 비워둘 수 없으며 끝에 마침표를 붙이지 않는다.
- 이슈 번호는 메시지 마지막에 `(#숫자)` 형식으로 하나만 쓴다.
- Git이 자동으로 만드는 merge, revert 등의 특수 커밋은 일반 작업 커밋 규칙의 예외로 둔다.
- `.husky/commit-msg`에서 commitlint가 이 형식을 자동으로 검사한다.

좋은 예:

```text
feat: 추천 결과 필터 기능 추가 (#12)
fix: 일정 카드 시간 표시 오류 수정 (#24)
refactor: 복구 폼 검증 로직 분리 (#31)
chore: 프로젝트 초기 개발 환경 설정 (#35)
docs: Git 협업 흐름 문서화 (#42)
```

피해야 할 예:

```text
feat: 여행 일정 입력 기능 구현        # 이슈 번호가 없음
Feat: 여행 일정 입력 기능 구현 (#12)  # type이 소문자가 아님
feat 여행 일정 입력 기능 구현 (#12)   # 콜론과 공백이 없음
feat: 여행 일정 입력 기능 구현 (#abc) # 이슈 번호가 숫자가 아님
feat: 여행 일정 입력 기능 구현 (#12). # 이슈 번호가 메시지 마지막에 없음
feat: 여행 일정 입력 기능 구현. (#12) # subject 끝에 마침표가 있음
fix: 카드 수정 및 폴더 구조 변경 (#24) # 서로 다른 관심사가 섞임
```

커밋 하나는 되돌려도 다른 기능이 깨지지 않는 **하나의 논리적 변경**으로 만든다. 예를 들어 타입 정의, 해당 타입을 쓰는 API 함수, 그 작업에 필요한 테스트는 함께 커밋할 수 있다. 반면 기능 구현과 무관한 포맷 정리, 의존성 업그레이드, 별도 버그 수정은 나눈다. 너무 잘게 쪼개 파일 하나마다 커밋할 필요는 없으며, 로컬의 시행착오 커밋은 PR 전 정리할 수 있다.

## 5. Pull Request 운영 기준

### 생성 시점과 범위

- 독립적인 완료 조건을 충족하고 리뷰받을 수 있을 때 PR을 만든다.
- 방향을 일찍 공유할 필요가 있으면 Draft PR을 만들고 준비되면 Ready for review로 전환한다.
- 하나의 PR은 하나의 Issue 또는 하나의 명확한 목적을 기본으로 한다.
- 기능 구현과 대규모 리팩터링을 같은 PR에 섞지 않는다.
- 가능하면 변경 파일 10개 안팎, 순수 변경 300줄 안팎을 권장 기준으로 삼되 자동 생성 파일과 단순 반복 변경은 예외로 한다. 숫자보다 리뷰어가 한 번에 맥락을 이해할 수 있는지가 우선이다.
- 리뷰에 30분 이상 걸릴 것으로 예상되거나 설명에 여러 개의 독립적인 완료 조건이 생기면 분리를 검토한다.

PR 제목은 커밋과 같은 형식으로 작성한다.

```text
feat: 상세 복구 일정 입력 기능 구현 (#12)
fix: 추천 카드 모바일 레이아웃 수정 (#24)
chore: 프로젝트 폴더 구조 및 아키텍처 가이드 추가 (#35)
```

PR 본문에는 최소한 다음 항목을 포함한다.

- 작업 내용과 변경 이유
- 주요 변경 사항
- 검증 방법과 결과
- 관련 Issue: `Closes #12`, `Fixes #12` 또는 `Refs #12`
- UI 변경 시 전/후 스크린샷 또는 짧은 영상
- 리뷰어가 특히 확인할 부분(있는 경우)

`Closes`/`Fixes`는 merge와 함께 Issue를 닫을 때, `Refs`는 관련만 있고 자동 종료하면 안 될 때 사용한다. 반응형 레이아웃, 화면 상태, 시각적 버그 수정은 스크린샷을 첨부한다. 문서·설정·내부 로직만 변경했다면 생략할 수 있다.

작성자는 리뷰 요청 전에 diff를 처음부터 읽는 **self review**를 하고 디버그 코드, 불필요한 파일, 오탈자, 검증 누락을 제거한다. Draft가 아니고 CI 또는 로컬 검증이 통과한 뒤 다른 FE 1명에게 리뷰를 요청한다. 긴급 장애가 아니라면 작성자 외 FE 1명의 승인을 받은 후 merge한다. BE 계약이나 API에 영향이 있으면 BE 담당자에게도 해당 부분 확인을 요청한다.

## 6. Merge 방식

| 방식             | 특징                                              | 이 프로젝트에서의 판단                                   |
| ---------------- | ------------------------------------------------- | -------------------------------------------------------- |
| Merge commit     | 브랜치의 모든 커밋과 merge commit을 보존한다      | 시행착오 커밋까지 남아 `main` 이력이 복잡해질 수 있다    |
| Squash and merge | PR의 커밋을 하나로 합치고 PR 연결 정보는 유지한다 | **작은 팀과 포트폴리오에 가장 적합**                     |
| Rebase and merge | 커밋을 선형으로 재배치해 개별 커밋을 보존한다     | 커밋 정리와 rebase 숙련이 필요하고 PR 경계가 덜 선명하다 |

기본 방식은 **Squash and merge**다. PR이라는 협업·리뷰 기록은 GitHub에 유지하면서 `main`에는 목적이 분명한 커밋 하나만 남길 수 있다. Squash 커밋 제목은 이슈 번호를 포함한 PR 제목을 그대로 사용하고 필요하면 본문에 핵심 변경을 남긴다. merge 후 원격과 로컬 작업 브랜치를 삭제한다.

## 7. 전체 작업 흐름 예시

예: `#12 [Feat] 상세 복구 일정 입력 구현`

```text
Issue 생성 및 담당자 지정
↓
최신 main에서 작업 브랜치 생성
↓
구현 및 논리 단위 commit
↓
push 후 PR 생성
↓
self review 및 로컬 검증
↓
다른 FE 1명 review
↓
Squash and merge
↓
작업 브랜치 삭제
```

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/12-recovery-form

# 구현 후 변경 범위를 확인한다.
git status
git diff
git add src/features/recovery
git commit -m "feat: 상세 복구 일정 입력 폼 추가 (#12)"

git push -u origin feat/12-recovery-form
# GitHub에서 PR을 생성하고 본문에 `Closes #12`를 작성한다.

# 리뷰 반영 후
git add src/features/recovery
git commit -m "fix: 복구 일정 종료일 검증 보완 (#12)"
git push

# GitHub에서 Squash and merge 후 로컬 정리
git switch main
git pull --ff-only origin main
git branch -d feat/12-recovery-form
```

다른 작업 중 `main`의 변경이 필요하면 PR merge 직전에 최신 `main`을 반영하고 충돌을 직접 해결한 뒤 다시 검증한다. 공유된 작업 브랜치에서 강제 push는 피한다.

## 8. 최소 리뷰 기준

리뷰어는 다음을 확인한다.

- 요구사항과 Issue 완료 조건을 충족하는가
- 구현이 필요 이상으로 복잡하지 않은가
- 컴포넌트와 hook의 책임 및 현재 feature-based 구조가 적절한가
- TypeScript 타입이 안전하며 불필요한 `any`나 단언이 없는가
- 중복 코드가 의미 있게 줄어들 수 있는가. 재사용 가능성만으로 성급하게 공통화하지 않았는가
- 로딩, 빈 값, 오류, 긴 텍스트, 모바일 등 예상 가능한 edge case를 다뤘는가
- 버튼 이름, label, 키보드 조작, 이미지 대체 텍스트 등 기본 접근성을 지켰는가
- 기존 UI와 스타일 및 네이밍이 일관적인가
- 불필요한 client boundary, 렌더링, 네트워크 요청이 없는가
- lint/build/test 등 필요한 검증 결과가 있는가

리뷰 코멘트는 취향보다 **문제의 이유와 개선 방향**을 함께 쓴다. 중요도를 명확히 하기 위해 필요한 경우 다음 표기를 사용한다.

```text
[blocking] 종료일이 시작일보다 빠를 때 API 요청이 발생합니다. submit 전에 날짜 순서를 검증해 주세요.
[suggestion] 이 분기는 별도 함수로 추출하면 테스트와 읽기가 쉬워질 것 같습니다. 이번 PR에서 필수는 아닙니다.
[question] 이 상태를 전역으로 둔 이유가 있을까요? 현재 화면에서만 사용한다면 로컬 상태로도 충분해 보입니다.
```

작성자를 평가하는 표현은 피하고 코드와 영향에 집중한다. 단순한 선호는 blocking으로 다루지 않는다.

## 9. 작업 크기 판단

| 구분           | 기준                                                       | 예시                                           | 처리 방식                                                       |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------- |
| 매우 작은 작업 | 동작 영향이 없거나 명백한 소규모 수정, 논의 불필요         | 문서 오탈자, 주석 수정, 단순 문구 교체         | Issue 생략 가능. 작은 PR 권장, 예외적으로 `main` 직접 수정 가능 |
| 일반 작업      | 독립적인 완료 조건이 있고 리뷰 가치가 있음                 | 폼 구현, API 연동, UI 버그, 공통 컴포넌트 개선 | Issue 1개 + 작업 브랜치 + PR 1개                                |
| 큰 작업        | 여러 화면/계층, 독립 배포 가능한 단계, 리뷰 30분 이상 예상 | 복구 흐름 전체, 인증 도입, 상태 관리 구조 전환 | 상위 Issue 1개에 체크리스트/하위 Issue를 두고 여러 PR로 분리    |

큰 기능은 예를 들어 `타입·API 계층 → 입력 UI → 결과 UI → 통합`처럼 각각 main에 합쳐도 안전한 순서로 나눈다. 단지 줄 수를 맞추기 위해 강제로 쪼개거나, 반대로 Issue 하나를 끝내기 위해 거대한 PR을 만들지 않는다.

## 10. 빠른 체크리스트

작업 시작 전:

- 최신 `main`에서 목적이 분명한 브랜치를 만들었는가
- 추적 가치가 있는 작업이면 Issue와 완료 조건이 있는가

PR 요청 전:

- 한 가지 목적만 담았는가
- self review와 필요한 lint/build/test를 완료했는가
- Issue 연결, 검증 결과, UI 스크린샷을 적었는가

Merge 후:

- Squash 커밋 제목이 convention에 맞는가
- Issue가 올바르게 닫혔는가
- 작업 브랜치를 삭제했는가
